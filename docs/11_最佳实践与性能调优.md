# 11 最佳实践与性能调优

## 1. 写入

- **批量写入**：一次 insert 几百到几千条，远快于逐条写；
- **控制单条大小**：大文本先切块，不要把整本书塞进一个 VARCHAR；
- **避免频繁 flush**：flush 会生成新 segment，增加小文件与索引构建成本；
- **upsert 有代价**：会写入新版本并产生旧数据，靠 compaction 回收；
- **主键稳定**：不要用时间戳等每次都变的值做主键。

本项目 `insert_in_batches` 默认每批 64 条，便于观察；生产可以调大到 500–2000。

## 2. 索引与加载

- 小数据（< 10 万）先用 FLAT，简单且精确；
- 在线低延迟优先 HNSW，`M=16`、`efConstruction=200` 起步；
- 内存敏感考虑 IVF_SQ8 / HNSW_SQ；
- 建索引是重操作，尽量在数据导入完成后一次性构建；
- `load_collection` 会把数据/索引加载到内存，注意容量规划。

## 3. 查询

- `output_fields` 只取需要的字段，别把大文本全部带回；
- 过滤条件尽量命中标量索引；
- 高选择性过滤 + 向量检索时，适当增大 `ef`/`nprobe`；
- 深分页用迭代器，不要无限增大 `offset`；
- 多路召回时，先控制每路 `limit`，再融合。

## 4. 容量估算（粗略）

内存主要被以下部分占用：

```text
原始向量：N × dim × 4 bytes
HNSW 图：  N × M × 2 × 4 bytes 左右（量级估算）
标量字段：按类型与长度估算
索引结构：标量/稀疏倒排的额外开销
```

例子：100 万条 × 768 维 float32：

```text
向量原始数据 ≈ 1e6 × 768 × 4 ≈ 3.07 GB
HNSW(M=16)   ≈ 1e6 × 16 × 2 × 4 ≈ 128 MB
```

实际还要加上 segment、副本、查询节点缓存等，建议预留 1.5–2 倍余量。

## 5. 观测指标

| 指标 | 说明 |
|---|---|
| QPS | 每秒查询数 |
| P50/P95/P99 延迟 | 尾延迟比平均值更重要 |
| Recall@K | 与 FLAT 基线对比 |
| 索引构建时间 | 数据量/参数变化时关注 |
| 数据/索引文件大小 | 容量与 compaction 观察 |
| 过滤命中率 | 判断过滤条件是否过严 |
| 错误率 | 连接、超时、表达式错误 |

小项目可以先用计时日志；生产接入 Prometheus/Grafana 或云监控。

## 6. 安全

Milvus Lite：

- **无鉴权、无 RBAC、无 TLS**；
- 不要暴露在不可信网络；
- 适合本机学习/原型。

生产：

- 启用鉴权与 TLS；
- 按最小权限分配角色；
- 不要把 API Key、连接串提交到仓库；
- 对用户输入做长度与内容校验，避免表达式注入。

## 7. 常见坑清单

1. 建了 COSINE 索引，搜索却传 L2 参数；
2. `ef < limit`，召回明显下降；
3. 中文 BM25 没启用中文分析器，关键词搜不到；
4. 过滤表达式用了单引号包字符串；
5. 分区名用中文导致创建失败；
6. 同一数据目录被两个进程打开，报文件锁；
7. 忘记 `load_collection` 就查询；
8. 指望 `delete` 立即释放磁盘（实际要等 compaction）；
9. 用伪向量评估真实业务效果；
10. 把 `VARCHAR` 的 `max_length` 设得过大，浪费内存。
