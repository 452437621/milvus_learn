# 09 混合检索与重排序

## 1. 为什么要多路召回

稠密检索擅长语义，但在以下场景会失手：

- 专有名词、编号、代码符号（“HNSW”“RFC 7231”）；
- 用户明确要搜某个关键词；
- 短查询、领域术语与训练语料不匹配。

BM25/稀疏检索正好互补：它对精确词项敏感，但不理解同义改写。
**混合检索**把多路结果融合，通常能同时提升召回率和稳定性。

## 2. Milvus 的混合检索接口

```python
from pymilvus import AnnSearchRequest, RRFRanker, WeightedRanker

dense_req = AnnSearchRequest(
    data=[query_vector],
    anns_field="embedding",
    param={"metric_type": "COSINE", "params": {"ef": 64}},
    limit=10,
)
sparse_req = AnnSearchRequest(
    data=[question_text],
    anns_field="sparse",
    param={"metric_type": "BM25", "params": {}},
    limit=10,
)

results = client.hybrid_search(
    collection_name="docs",
    reqs=[dense_req, sparse_req],
    ranker=RRFRanker(60),
    limit=5,
    output_fields=["title", "category"],
)
```

注意：

- 每个 `AnnSearchRequest` 有自己的 `anns_field`、`param`、`limit`；
- 最终 `limit` 是融合后的返回条数；
- 不同版本的参数名可能略有差异，以 `00_environment_check.py` 的签名为准。

## 3. RRF（Reciprocal Rank Fusion）

RRF 只看排名，不看原始分数，因此天然解决“分数尺度不同”的问题：

```text
RRF(d) = Σ 1 / (k + rankᵢ(d))
```

- `rankᵢ(d)`：文档 d 在第 i 路结果中的名次（从 1 开始）；
- `k`：平滑常数，常用 60；
- 某路没召回到的文档，该路贡献为 0。

优点：简单、稳健、无需调权重。
缺点：丢掉了分数强弱信息；如果某一路明显更可靠，无法体现。

## 4. WeightedRanker

```python
ranker = WeightedRanker(0.7, 0.3)
```

- 每个权重对应一路召回；
- 权重通常需要归一化（总和为 1）；
- 不同路的分数需要先归一化到可比较范围，否则大尺度分数会主导结果。

适合你对各路质量有明确先验的场景，例如“稠密 0.7、BM25 0.3”。

## 5. 融合之后还要重排吗

两阶段检索很常见：

1. **召回**：向量/BM25/混合，取较多候选（如 50–200）；
2. **重排**：用 cross-encoder 或业务规则精排，取最终 Top-K。

重排模型精度更高，但延迟和成本也更高；适合对相关性要求高的场景。
Milvus 支持请求级 rerank（模型 rerank、数值衰减 rerank），
本项目只演示 RRF/加权融合，避免引入额外模型依赖。

## 6. 去重与多样性

- 同一文档的多个 chunk 可能同时命中，需要按 `doc_id` 去重；
- 可以用 `group_by_field` 按文档分组，每组只返回若干条；
- RAG 中通常限制每个文档最多保留 1–2 个 chunk，避免上下文被单一文档占满。
